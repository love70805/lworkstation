## 用户反馈与已确认原因

用户：“针对表格的改动仍未生效，小灯点击展开状态文本太复杂太冗杂，其实仅用灯的颜色不同就可以。”随后明确表格问题来自“下载已有报告，仍有‘核算采购’或多条关联单号”。

代码确认：Beta.9 的 `buildProfitReportWorkbook` 已简化新报告，但 `downloadReportFile` 仍直接将已存 `fileBase64` 下载；`MonthlyReportManager.jsx` 的当前报告下载及历史重下载均使用该函数。此前将旧文件原样下载视为兼容，没有满足用户这条实际下载路径。

## 1. 已有报告下载应用简化格式

- 当前报告和历史报告的常用下载路径均应得到简化表格：无“核算采购”工作表，每个商品行关联单号只保留一条，汇总及店铺页一致。未扣款和财务对账两种都覆盖。
- 只从该报告保存的冻结数据或原始工作簿派生下载副本；不得读取最新台账/ERP数据重新计算历史利润，也不得覆盖原始存储文件、原报告 hash、指纹、版本、日期、金额或定稿状态。不执行真实数据库迁移或批量改写。
- 单号使用该报告实际核算采购中的首个有效单号，顺序沿用最近在前；同笔优先1688号，否则采购单号/ID。证据缺失的旧报告按已有汇总串的已知分隔格式安全兼容；不能误拆单号本身的斜线，保留前导零和长数字文本。
- 现有新报告简化导出继续有效；显示简化不得缩减内部三笔加权成本或完整证据。
- 下载按钮及文件身份表述准确：普通简化下载不能仍误称原封不动的原文件。保留原始存档作为审计依据；若保留显式原文件下载，应与默认简化下载清楚区分，避免主流程继续默认旧格式。
- 若旧报告信息不足或损坏，应明确反馈，不能伪造新明细、使用当前ERP替代历史证据或静默退回不符合要求的旧格式。

验收必须从真实 UI 下载入口触发，覆盖升级前生成的报告、应用重开后当前/历史报告、两种报告和新报告；读回实际下载的 XLSX，验证无采购sheet、每行单号一致，行数、金额、扣款/代发、长号与前导零保持。对比下载前后的数据库记录及原存档字节/hash，确保下载不写回、不触发重新定稿。只用隔离数据，不能只测底层新工作簿构造器。

## 2. 小灯只用颜色反馈

- 用户最新要求覆盖 Beta.9 的点击详情、悬停说明和首次就绪文字轻提示：现在只需小灯颜色变化，不再展开状态面板、悬停长文字、增加常驻文案或弹出就绪提示。
- 使用明确少量状态色：绿色表示真实且未过期的就绪，黄色表示检测/等待（包括需要登录），红色表示异常/断连。启动未知不能冒充绿色；具体内部状态可完整保留在诊断数据中，不堆到界面。
- 保留 Beta.9 的后台自动检测、握手真实性、失效撤绿和恢复更新；无需打开采购页或手动点击。移除点击处理、无效按钮语义和关联弹窗生命周期，不影响独立的版本更新弹窗、ERP正常登录/采集和1688功能。
- 保持灯尺寸、位置与主题一致，无持续闪烁，不抢焦点。不增加可见文字；可保留无视觉占位的读屏状态名称，不因技能通用建议而违背本次纯颜色要求。

验收鼠标点击/悬停、键盘与各种状态都不出现文字面板；浅深色、窗口化下状态颜色可辨；冷启动不打开采购页仍自动检测，握手就绪/过期/断连/恢复正确，重复事件不触发提示或隐藏窗口泄漏。可见性与真实账号未测部分须如实说明。
