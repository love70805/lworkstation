# 下一版 Beta：界面交互与核算流程完善

日期：2026-09-22。基线：`main d50343c` / 已发布 `0.3.0-beta.4`。

最新版本范围、实施顺序与发布验收已细化为 [Beta.5 更新计划](BETA_5_IMPLEMENTATION_PLAN.md)，以该文档为准；下文保留早期规划及检查后的补充依据。

状态：规划草案，供用户补充和调整，尚未获准实施。本次只形成方案。建议下一版继续 Beta 线，版本暂定 `0.3.0-beta.5`；软件版本号、发布资产及真实业务数据保持现状，本机暂不安装约定继续有效。

## 目标

让用户在任意页面都清楚当前账本月份、查看范围、实际处理范围和下一步；降低利润与 ERP 之间来回查找的成本，减少窗口化操作中的长页面、状态跳变和重复等待。

## 已有能力与业务基线

- 首页已具备每日堆叠、月度簇状、期间店铺扇形与销量 Top 5 SKC、搜索分页和相邻期间切换，保持当前布局方向。首页负责经营概览，利润页负责商品、成本及月度核算。
- 批量台账统一预览、一次确认，ERP 自动登记、分批回传，人工更正/撤销，两阶段报告和旧报告原文件下载已经存在，应完善使用体验而非重复建设。
- 已有本机持久化派生缓存与后台计算。后续性能工作先测量实际命中、失效和耗时，再针对瓶颈调整。
- 成本月份始终来自台账 `ledger.period`：当月及以前，按时间最近三笔、数量加权、单价四位截断。利润金额先精确累计、最后截断。
- 人工成本只需非负成本与说明，支持零和微小正数；优先级最高，限定工作区/月/店/SKU，可撤销。ERP 回传不能覆盖有效人工值。
- 默认按全部过仓计算仓储费；用户给定的整月代发总件数用于计算代发金额，统一加在汇总中。扣款独立按店铺归集。两份报告沿用已确认的左右布局、对齐和斑马纹模板，基础冻结与历史修订保留。

建议正常路径：

`选择台账 → 查看本月待办 → 取得成本 → 处理需要关注的项目并采用 → 登记整月代发 → 保存未扣款报告 → 后补各店扣款 → 保存财务对账报告`

这是对现有能力的入口整理。正常 ERP 成本采用后，无需额外填写人工成本；人工更正用于用户需要覆盖候选值的情况。最终写入、报告生成与定稿仍执行后台现有完整校验。

## 动效与界面细节

- 沿用中文、现有主题和主色；店铺颜色跨日期/月/页面保持一致，数量与金额用右对齐等宽数字，状态同时有文字。
- 页面只突出当前最重要的下一步；来源解释和技术详情按需展开。表格关键列优先可见，长文本不靠无限缩小字号解决。
- 按钮反馈约 100–150ms；抽屉、弹窗和局部状态变化约 160–220ms。优先透明度与轻位移，反馈不拖延保存或导航。
- 图表悬停只更新提示与高亮，不改变布局尺寸；已有图形类型保留。进入销售详情时补齐键盘焦点，相邻期间切换和 Escape 返回均可连续操作。
- 支持减少动态效果；连续切换时取消过时动画，输入焦点和滚动不被动画重置。

## 性能与稳定性

1. **首屏状态先正确。**首页/账本读取中保留结构，空数据仅在读取完成后显示；失败提供局部重试，保留当前范围。
2. **测量缓存的实际收益。**隔离 1 万/10 万行数据，记录冷启动、首次计算、同月返回、重启后命中、修改一个店铺成本后重算。当前派生缓存对业务库写入使用全局版本失效，需测量是否因无关写入产生多余重算。
3. **精准失效列为 P2 候选。**确认瓶颈后评估按工作区/账本/数据依赖失效；新策略必须覆盖导入替换、成本采用、人工更正/撤销、费率、备份恢复和规则升级，不以提速牺牲一致性。缓存始终可重建，定稿与报告依据真实来源。
4. **白屏问题继续跟踪。**已有前台恢复和故障提示，用户原机长时间偶发白屏尚未稳定自然复现。本版建议补本机有限诊断记录与长时间切页/最小化/系统睡眠恢复验收，区分渲染进程退出、页面无内容与响应超时；健康页面保留未保存输入，不因暂时后台状态自动重载。
5. **性能目标属于待测指标。**同机同数据下，热返回/局部筛选以 300ms 内开始反馈为目标；较长读取持续显示明确阶段。记录整页可用时间及慢样本，不以某一步计算耗时代替完整体验。

## 可后移的改善

- 代发/扣款导入先呈现工作表、本人筛选命中数、店铺覆盖与错误行；当前映射面板改为仅在需要时展开。采用范围仍由用户明确选择，不自动扩大到全表。
- 精准缓存失效在测量后确定是否纳入同版；不为 UI 规划预先引入业务数据库迁移。
- 云端部署、额外分析模块和跨月对比另行规划；当前交付继续为本机桌面 Beta。

## 整体检查后的追加与排序

用户要求整体检查后，完成[Beta.4 UI 与使用逻辑审查](UI_FLOW_AUDIT_2026_09_22.md)，记录 21 项问题/风险及 6 项流程改善建议，逐项标注浏览器复现、隔离执行或静态证据。此处更新的是规划草案，不自动扩大为已批准的软件实施。

- **优先保证正确性与恢复保护：**历史月导入不能跳默认上月；恢复前必须确认回滚备份保存成功；正式商品“保存草稿”不能绕过在售校验或误导保存结果。
- **先把成本流程走通：**人工有效值应解除对应候选异常的整批阻塞；已采用成本不再显示无法执行的采用动作；筛选无结果不能误报账本缺 SKC。
- **统一结果与提示：**财务报告生成后的概览利润来源明确；已定稿不再要求确认；刷新和连接状态必须反映实际结果。
- **补齐遗漏交互：**恢复系统检查直接入口、待采集返回位置、商品未保存保护、标签连续输入、供应商改价预览、空售价待查、下载取消与销售明细键盘焦点。
- 首页现有布局和图表类型继续保留。优先修复数据、流程和恢复问题，再做细节与动效，不让视觉优化挤占正确性修复。

## 实施顺序与验收

1. 先用现有布局做三个代表性预览：利润下一步与整月准备度、成本列表/侧面详情、报告准备区；包含正常、异常、已定稿、无数据、加载失败状态。
2. 实现月份/工作区传递与统一准备度只读模型，再接入各页面。避免每页独立维护一套状态条件；后台写入校验保持独立权威。
3. 落地成本就地处理、报告前置提示及返回状态；整合共享表格、弹窗、焦点、动效。
4. 完成读取/错误反馈和稳定性验收，根据基准决定是否加入 P2 缓存优化。
5. 在同一候选中完成回归、窗口交互和真实用户路径验收后统一发 Beta。方案讨论阶段不产生软件版本。

关键测试场景：历史月/系统月不一致；A 店已齐但 B 店缺成本；同范围子集回传；真实零与未取得；人工覆盖与撤销；输入后连续切页；第 2 页展开商品后往返成本页；基础定稿后补扣款；重下载旧报告不重算；批次迟到与跨范围拒绝；缓存命中/失效；ERP/1688 后台及睡眠恢复。冻结报告与人工优先级属于必须通过的回归项。

发布检查沿用项目现行全量前端测试/构建、适用桌面 verify/smoke、候选路径验收、PR 必需 CI、安装包哈希和公开资产回读。Beta 与稳定通道保持隔离，本机安装遵循现有暂不安装约定。

## 本次代码核对依据

这是代码审阅得到的风险与改进机会，不等同于全部已在用户现场复现。

- `CostMatching.jsx` 的检查映射入口传入账本参数；`ImportPreview.jsx` 初始化只使用 `previousMonth()`，未接收该参数。
- `WorkspacePortal.jsx` 工作区流程使用最新未完成账本，而销售区域使用筛选账本；需要明确各自范围。
- `ProfitPanel.jsx` 下一步提示主要依据当前筛选的缺成本数量；整月定稿条件使用全账本汇总，两者需要统一解释。
- `CostMatchingInboxDialogs.jsx` 部分匹配说明仍写完整集合完全匹配，与已有子集合同不一致。
- `MonthlyReportManager.jsx` 主要在预览动作后反馈准备条件；`profitReportRepository.js` 的检查可供页面准备度只读复用。
- `MonthlyLedger.jsx` 首次读取默认 `[]`；首页读取完成前有默认零值。需要将未读、空与失败区分。
- `ProfitGroups.jsx` 等局部组件的展开/页码随视图卸载丢失；销售详情进入焦点、多店图例高度仍可完善。
- `derivedCache.js` 已有持久缓存，任意业务库写入轮转全局版本；优化需先提供命中和失效证据。
- `AppShell.jsx` 侧边栏诊断项显示“备份中心”并跳转 `/data-security`，版本信息中却仍提示使用左侧“系统诊断”；`App.jsx` 的 `/diagnostics` 和 `Diagnostics.jsx` 功能均保留，桌面用户可暂从“成本核对 → ERP 扩展状态 → 系统诊断”进入。

本轮只保存规划，未改业务代码、数据库结构或软件发布状态。
