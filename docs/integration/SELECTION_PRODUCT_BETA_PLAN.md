## 流程需求

### 1. 无销售数据也可进入产品建档流程（已确认）

用户指出选品面板中没有销量、暂无定稿的ERP身份记录，也应可进入档案建立流程，不能以已有销售数据为前提。

用户随后纠正：本场景已有成本，仅缺少销售台账数据。不得把缺少销售台账等同于缺少成本，也不得因没有销售台账而丢失或误标已有成本；助手此前将“缺少成本”一并带入本条的表述不作为需求依据。

- 产品档案可以先于销售建立，后续销售记录按既有身份关联。
- 建档入口资格与销售历史、利润参考状态分开；“0个月/0件”“暂无定稿”等状态不应禁用或隐藏建档入口。
- 没有销售台账时如实标注缺少销售历史，已有成本仍应保留并正确展示；不得据此将成本显示为缺失，不虚构销售额或实际利润。
- 验收：同等建档条件下，有销量与无销量的未建档记录均能进入流程；不要求先导入销售台账或完成月度定稿。
- 本条仅确定进入流程的条件，不预设最终保存所需字段、自动创建或批量建档行为，等待后续逐条规划。

此要求与选品档案、月度核算职责分离的业务规则一致。当前仅记录，未断言现有程序已满足，未修改实现。

### 2. 从已售SKU展开ERP关联的未售SKU（已确认）

用户明确数据关联路径：销售台账中的平台SKU对应平台SKC；平台SKC在ERP映射到仓库SKU，仓库SKU下又有对应的平台SKU。用户随后强调同仓库SKU下可能存在非本人SKU，并说明ERP仓库SKU信息中同时提供平台SKC和平台SKU，可提取对应关系。因此，补全范围须由本工作区已确认的平台SKC约束，不能将整个仓库SKU下的平台SKU全部纳入。

- 发现路径：台账已售平台SKU → 台账已确认的平台SKC → ERP仓库SKU映射 → 提取平台SKC与平台SKU对应关系 → 仅补全匹配已确认SKC的平台SKU，包括其中无销售记录的SKU。
- 商品身份和建档候选不能只取台账已售SKU集合，也不能扩大为同仓库全部SKU；应按ERP明确的SKC/SKU对应关系筛选，不假定SKC、仓库SKU、平台SKU之间一一对应。
- 用户进一步确认销售人员字段不一定准确，归属以本工作区已确认的SKC和ERP明确的SKC—SKU对应关系为准。销售人员不参与纳入、排除、冲突判断或新品归属推断；店铺可保留为来源信息，不额外设为本条的建档筛选前提。平台SKU按工作区全局唯一口径去重，已有SKU的SKC关系若与ERP冲突，不静默改绑。
- 同仓库SKU中属于其它SKC的记录不自动纳入；缺少SKC或映射冲突时不凭共享仓库SKU猜归属。台账中从未出现、也未通过其它方式确认属于本工作区的整个SKC，归属如何确认尚未规划，不在本条中自动扩展。
- 已售与未售SKU按真实平台SKC关系归组，保留平台SKU、仓库SKU的映射与资料来源；无销售记录的SKU同样可进入建档流程。
- 成本沿实际仓库SKU及ERP采购成本关联获取，不以该平台SKU出现在销售台账中为必要条件；是否有销量与是否能取得成本分开判断，不把所有展开SKU无条件复制为同一成本。
- 销售数据仍仅来自真实台账。ERP展开的SKU不能凭空生成销量、销售额、实际利润或月度定稿记录。
- 验收场景：某已确认SKC只有部分SKU出现在台账中，经ERP映射后，同SKC下其它关联SKU可被识别并用于建档；同仓库其它SKC的平台SKU不会混入。其中可取得ERP成本的正确关联展示，销售历史仍如实为空。

本条记录用户确认的关联逻辑；下方已完成ERP页面样本核验，但尚未核实当前扩展及工作台是否完整覆盖此路径。当前继续规划，不实施。

### ERP页面只读核验（2026-09-29）

用户授权查看其已打开的ERP。通过“商品档案”的SKU查询框，输入此前用户报告中的已知平台SKC，实际返回4个仓库商品；其中包含共用的引流商品，仓库编码与目标SKC并不相同。因此不能依靠仓库编码前缀或商品名称推断完整映射。

- “映射关系”明细实际提供：所属平台、平台SKU、平台SKC、店铺、销售人员，可从页面提取成对关系。
- 共用仓库商品的映射中，同一店铺下同时出现目标SKC/本人销售人员与其它SKC/其它销售人员，验证了仅凭仓库SKU或店铺不足以确认归属。
- 该仓库商品的创建人、开发人与目标映射行的销售人员不同，不能用仓库商品创建人或开发人替代平台SKU的归属。
- 商品档案显示单价与规格比例，但该单价不是已验证的月度ERP正式采用记录。本次未读取本机数据库、未核算采购批次，也未确认截图中每个未售SKU的实际成本状态。

核验后的确认口径：直接用本工作区已确认的平台SKC查询ERP商品档案，取得关联仓库商品后，按明确的SKC—SKU对应关系筛选并补全SKU；成本再沿各SKU真实仓库映射及规格比例关联。用户指出销售人员字段不一定准确，因此撤回此前以销售人员辅助判断归属或发现全新SKC的建议。页面存在该字段不代表其归属内容准确。全新且尚未确认归属的SKC仍不自动纳入，等待后续规划。

本次仅确认页面字段和样本关系可用，未验证扩展自动采集的完整性，未修改ERP数据、业务代码或真实数据库。

### 成本来源核对（当前实现事实，非新增需求）

在0.3.2源码中，选品参考页从本机 `erpCostRows` 读取ERP回传历史成本，按平台SKU归集并通过成本策略选取有效记录；没有有效ERP记录时，现有逻辑再查选品人工确认、定稿历史、供应商参考成本。ERP目录信息 `catalogRows` 可提供身份与建档资料，但“身份来自ERP”不等同于该SKU已取得有效ERP成本。销售台账提供销售/身份数据，不从销售额倒推采购成本。

上文“已有成本”是用户说明的本场景前提及应支持的业务情况，尚未通过用户真实本地数据库逐条核实截图SKU成本记录。不能将此表述为已证实界面误判，也不能把缺销售台账作为成本必然缺失的理由。本阶段未读取或修改真实库。

### 3. 建档表单精简与自动填写（已确认，2026-09-29）

用户提供当前建档页、ERP档案资料及1688来源报价截图，要求减少填写项、从已有数据自动填写，并优化整体界面。本条仍纳入Beta规划，未启动实现。

已确认的产品行为：

- 商品标题从已关联仓库SKU的名称提取，自动填写中文商品名称；不再要求英文名称，移除英文标题输入及相关缺失提示。
- 标签根据真实销量自动填写。用户最新改为近7天销量：≥700爆款、100–699高销、10–99一般、0–9低销，按最新要求将热卖并入高销、较低并入一般，覆盖此前按月三档及七天六档决定。用户进一步确认台账为历史整月完整数据，因此采用最新完整台账月份的月末为截止日统计7天（如8月25—31日），不使用最后销售行或导入日期，并明确只能通过台账获取销量；本批排除官方销量API、店铺授权及实时销量同步。现有日统计使用台账“添加时间”，不能用月合计估算七天，也不能把缺日期或覆盖不足当作低销量；标签显示实际日期范围，台账变更后自动重算。ERP仍用于商品资料和成本，不提供销量替代值。详见升级方案第7节及7.1节。
- 移除表单中的1688商品ID、供应商编号；保留1688来源链接与供应商名称。这里的ID指截图中的1688商品ID，不移除平台SKC、平台SKU和仓库SKU等必要映射标识。内部关联标识可保留，用户无需填写。
- 移除运费、操作费、包装重量输入，覆盖主供应商和其它供应商的重复输入区域；同步清理这些字段的缺失提示与资料完整度扣分。界面移除不等于授权清空历史值或改写已有成本。
- 移除发布平台输入。发布状态与选品状态合并为一个“状态”，允许手动调整。用户确认保留测品、待审核、采购中、观察中等现有阶段，只合并重复状态，保留已有自定义状态。
- 从利润核算取得资料并新建的产品档案，状态统一默认“已上架”。默认值不能在后续同步中覆盖用户已经手动调整的状态；其它建档来源保持原默认规则，合并后的完整选项与旧状态映射见完整升级方案第8节。
- 右侧校验与保存流程须匹配精简后的表单，不再要求填写已移除的字段；有有效ERP成本的档案，不应因未填写1688参考报价而被当成缺少建档成本或要求重复填写。
- 用户确认：名称与SKC—SKU关系明确即可保存；缺图片、供应商链接或部分SKU成本只标注缺项，允许保留“已上架”。已上架只表示商品状态，不代表资料全部齐全或所有SKU均可月度核算。

采购总份数的代码核对：0.3.2的 `ProductEditor.jsx` 将各规格 `purchasePackCount` 相加；`erpProductCatalog.js` 为新增ERP规格默认填写1份，因此带入4个SKU且未修改时显示4份。该值用于1688参考报价中的整单运费分摊，不是ERP实际采购数量或销量，也不代表4笔采购。助手建议随本次表单精简移除该汇总展示，避免将默认参数误解为业务事实；规格换算关系仍须保留，不能因移除显示而破坏成本换算。

界面方案建议（待后续整体确认）：

- 页面集中为商品基本信息、SKU规格与成本、供应商来源三个区域；图片、中文标题、状态和自动标签优先展示，SKC及关联店铺信息紧凑排列。
- SKU规格表逐行对齐规格、平台SKU、仓库SKU及已有成本；ERP原始资料和采购证据按需展开，避免与编辑表单重复铺满页面。
- 将右侧大面积“入库校验”收敛为字段旁必要提示与简短保存反馈，取消无实际意义的缺失警告，完整度指标随有效字段重新评估。使用技能优先级表中的表单就近报错和渐进展示通用指导；本次技能搜索未返回匹配的渐进展示专项条目，不将搜索结果当作此方案的依据。
- 标题建议剔除可明确识别的数量、颜色、人员/店铺后缀，提取主体商品名并允许手动修订。截图存在主体“收腰神器”和配件“备用毛巾扣”混在同SKC的情况，不能简单采用首条名称、机械公共子串或把配件名作为父级标题；主体判定规则待细化，无法可靠区分时提供候选，不强行猜测。已有人工标题不被后续同步覆盖。

验收应覆盖：ERP资料预填、多颜色与引流配件混合名称、无销量可建档、移除字段不再触发警告、核算来源默认已上架且可手动调整、手动状态不被再次同步覆盖、历史费用与成本不被界面精简静默改写。布局沿用现有中文桌面风格，实施时验证窗口化、窄屏及浅深色。

### 4. 利润核算过程中备齐可直接建档的资料（已确认）

用户要求“尽量能实现利润平台核算过程中就能获取足够信息可以直接建档”。核心目标是复用一次台账导入和ERP成本核算过程，尽可能同步取得建档所需资料，减少再次打开ERP查询、重复采集和手工录入；不是将核算完成或月度定稿设为建档前提。

- 台账提供已确认的SKC—SKU关系、店铺、销售数量及收入；销量标签沿已确认的历史完整台账月末七天规则生成，不把历史成交价直接当作当前售价。
- ERP在核算查询过程中同步取得可用的仓库商品名称、平台SKC/SKU与仓库SKU对应关系、规格、图片、供应商名称及1688商品链接，并保留来源。按已确认SKC补全其中没有销售记录的SKU，销售人员不参与归属判断。
- 各SKU关联其真实可用的ERP成本及采购证据；已采用的有效人工成本仍按原优先级保留。1688链接用于商品来源，不要求用户重新输入1688采购价才能建档，也不把参考资料自动升级为月度正式成本。
- 核算时获取的资料须随回传可靠保存到本机，建档页复用已收件资料预填，避免用户再次查询。同一商品已经建档时识别并打开已有档案，不重复创建、不覆盖用户修订的标题和状态。
- 目标用户路径：导入台账 → ERP核算并同步收集资料 → 点击建立档案 → 预填商品信息、SKU、成本和来源 → 资料满足保存条件时直接保存。核算来源新档案默认“已上架”，可手动调整；“直接建档”不擅自解释为核算后无人确认自动创建全部档案。
- 缺失或冲突时只提示实际需要处理的项；ERP未提供的图片、属性、供应商或链接不得伪造，也不以非必需资料缺失制造重复确认。标题主体识别和身份冲突继续按本规划处理。

实施建议：建档资料收集与月度核算结果分开记录完成情况，附加资料获取失败可补取，不使已经有效的核算结果失败；核算成功也不能被误报为建档资料全部齐全。先复用已有查询结果与本机资料，对缺项按需补取，具体查询与回传契约在实施前细化。

验收目标：ERP实际提供必要资料的样本，一次核算后无需再次打开ERP或重新填写已有数据即可保存档案；同SKC未售SKU可一并带入；共享仓库其它SKC不混入；资料部分缺失时已有有效成本保持，只有必要缺项需补充；重复回传和重复建档不产生重复商品，不覆盖人工修订。本条为目标与规划，尚未验证整条自动采集、持久化及建档路径。

## 业务边界

沿用现有平台SKC父级、SKU属性分支和工作区唯一标识口径。选品商品档案与月度正式成本保持职责分离，建档流程不能静默改变已采用成本或已定稿利润。具体改动以用户后续明确要求为准。
