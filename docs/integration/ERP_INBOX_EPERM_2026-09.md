# ERP 收件文件 Windows EPERM 修复

## 用户场景与基线

2026-09-09：另一台 Windows 上运行正式 0.2.8，ERP 成本回传时出现 `EPERM rename erp-inbox.json.tmp -> erp-inbox.json`。无法直接访问该电脑，具体文件占用者或属性尚未确认。

基线：集成分支 b2ce9b2、main 53957bf，文件树相同；公开 0.2.8 代码包含下述缺口。

## 定位与复现

- HTTP 仅 POST 请求进入 spoolWriteChain；GET 状态轮询也会过期化请求并写回文件，未进入队列。
- 写入共用固定 `.tmp`，rename 没有短暂占用重试，GET/POST 竞争可使同一个临时文件被覆盖或提前重命名。
- 主线合成真实 HTTP 复现：15 GET 与 5 POST 并发，仅在测试侧延迟 rename 40ms，出现 12 个 ENOENT 失败（含一个 POST）。此测试没有向文件系统注入错误。
- 主线 Windows 合成文件短暂只读 300ms：真实 rename 产生 EPERM，旧版立即返回 400，目标原文件字节保持原样。本地复现说明缺乏短暂拒绝的恢复能力，不等同于确认远端只读或占用原因。

## 修复边界与目标

主责“利润与 ERP”，同步集成基线后只修改收件服务及测试。所有可能写入的读改写进入同一队列；有界读取 POST body，避免慢上传持有全局写队列；每次写入使用本次独占的同目录临时文件；对 EPERM/EACCES/EBUSY 做有限退避；失败保留原文件且释放队列。不先删目标、不直接覆盖、不放宽用户权限、不清空收件文件。

保持鉴权、数据格式、业务规则、成本发布、幂等、历史账本及数据库不变。不新增运行时模块或生产故障开关。新包发布与用户另一台电脑验收须单独记录，不能把代码集成表述为该电脑已修复。

## 验收

定向测试覆盖并发 GET/POST 无丢写、慢 body、瞬时/永久写入拒绝、失败原字节保留、后续请求恢复、批次重试幂等和他人临时文件保留。主线独立复现脚本重复验证修复，集成前完成前端测试与构建、桌面 verify、ERP 桥接与 inbox 检查。

合成复现证据位于本机 `archive/erp-inbox-eperm-2026-09-09/`，没有读取或复制用户远端业务文件。具体交付与最终验证结果在集成后追加。

## 已完成实现与主线审查

专职提交 4123774，主线承接 6c74307；只修改收件服务及两份测试。重命名最多尝试六次，退避20/40/80/160/320ms；不改变数据格式和发布幂等。主线独立复测并发请求零失败、五条POST全部保存；原生Windows临时只读300ms后HTTP202、约400ms恢复写入且原记录保留。原inbox与新spool测试、桥接检查、前端80文件/552项测试和生产构建、11组desktop verify通过。
