# ERP 成本采集速度基准与瓶颈诊断

2026-10-27 完成本机隔离测试。实际联网核对基线 `354232e8f47b9817e92e157dac196d704eec7666`，源码/稳定版 1.0.2，Electron 44.9.1。只新增基准工具、合成夹具和本报告；生产采集策略、并发上限、业务库、队列、登录配置和版本均未变更，无软件发布。

## 结果与建议

主要等待来自采购明细请求，其次是收件与采用状态的定时检查。在本夹具中，现有自适应并发上限由 8 提至 12，正常/慢响应总历时分别缩短约 18%/23%；发生一次 429 后，三组都降到 2 路，约 15.4 秒完成。没有证据支持继续提高生产上限。

建议下批优先评估收件事件通知与采用完成通知，保留低频轮询作为恢复保障；不要直接把产品改成 25 ms 轮询。其次记录真实任务各接口延迟、请求量和限流长尾，再确认 ERP 是否支持合并明细读取。继续保留完整采购历史、目标身份约束、分批持久回传和失败重试。以上为后续建议，本批未实施。

## 方法与边界

- 10 个合成 SKC/SKU，分为两批；每目标 48 条采购历史，共 480 条。每目标另返回一条越界映射，验证排除。每行销售数量 2、收入 CNY 100、单件仓储费 0.7；ERP 成本应为 5，单行利润应为 88.6。
- 比较测试副本的 8/10/12 路上限，保留生产初始 8 路、健康响应升速、429 降至 2 路、退避与 30 秒恢复冷却。四种场景各三次，共 36 次；每轮轮换配置顺序，测量时不并行运行构建或业务测试。
- 正常/慢响应夹具分别延迟 35/110 ms，这只是合成服务等待，不是真实网络延迟。429 场景在同一首个明细请求返回一次 429，`Retry-After: 1`；超时矩阵仅在临时副本将单请求期限缩为 500 ms。另用生产 120000 ms 期限实等一次。
- 使用隐藏 Electron 扩展、消息桥、独立本机收件服务、真实 Chromium IndexedDB 和实际成本 repository/利润 Worker；所有窗口不可见。各次独立会话、数据库和收件文件，进程使用独立测试 profile；ERP HTTPS 请求全部被夹具截获，不使用真实账号或业务资料。
- 主矩阵由 25 ms 测试轮询触发实际本机采用，隔离采集与核算开销。没有挂载完整 App，未测量其收件 ACK、旧草稿恢复和所有后台任务。另以固定 5000 ms 调度做三次对照，加上相同 25 ms 调度三次，共 **43 次**。
- “冷计算”是两批 `runCalculation` 历时之和；“成本就绪”截至最后一批实际采用和利润计算完成；“任务墙钟”从点击采集到采集器完成，包括其采用确认及资料补全。均不包含启动/建库，也不能视为完整产品 UI 耗时。
- “热计算”只对同一已验证任务的相同证据再计算，包含一致性核对耗时；它不是新任务、重启或登录变化后的缓存复用，也不据此承诺实际用户提速比例。

## 重复测量

受控任务墙钟，单位秒；格式为 **中位数 [最小–最大]**，每格三次。

| 场景 | 上限 8 | 上限 10 | 上限 12 |
| --- | --- | --- | --- |
| 正常响应 | 5.390 [5.387–5.399] | 4.734 [4.691–4.736] | 4.441 [4.419–4.465] |
| 慢响应 | 11.753 [11.549–11.798] | 10.024 [9.978–10.042] | 9.004 [8.964–9.069] |
| 一次 429 后重试 | 15.460 [15.329–15.479] | 15.377 [15.351–15.438] | 15.421 [15.405–15.506] |
| 一次超时后重试（500 ms 测试期限） | 5.487 [5.416–5.490] | 4.747 [4.736–4.757] | 4.498 [4.457–4.544] |

成本就绪中位数：正常响应为 **4.365 / 3.708 / 3.441 秒**，慢响应为 **10.742 / 8.965 / 7.987 秒**，顺序均为 8/10/12。上限 12 的正常冷计算中位数为 2.917 秒。429 的微小组间差异不构成上限收益；本夹具在 30 秒冷却结束前完成，未测量冷却后重新升速。

正常/慢响应均为 **560 次请求**：目录 10、映射 10、采购列表 60、明细 480，无重复请求。故障组均为 **561 次**，仅故障明细重试一次，最终失败为零。所有同任务热计算均为 **0 次 ERP 请求**，主矩阵历时 39.6–64.1 ms（含语义核对）；资料补全复用既有证据，没有额外 ERP 请求。

生产超时期限的单次对照：首个明细实际超时后重试，冷计算 122.165 秒、成本就绪 122.720 秒、任务完成 **123.747 秒**，561 次请求且结果一致。此项为单次恢复验证，不提供波动估计；不能将 500 ms 矩阵外推成真实慢请求速度。

## 等待发生在哪里

上限 12、正常响应三次中位数。以下区间相互重叠，不能相加得到总历时。

| 阶段 | 观测结果 |
| --- | --- |
| 所有 ERP 请求 | 实际请求区间并集 2.850 秒；并行累计 24.920 秒 |
| 采购明细 | 480 次，占请求数 85.7%；区间并集 2.396 秒，累计 21.334 秒 |
| 采购列表 / 目录 / 映射 | 请求区间并集分别 1.079 / 0.260 / 0.092 秒 |
| 并发槽排队 | 区间并集 0.659 秒，累计 1.520 秒；大部分与在途请求重叠，不能当成系统空闲 |
| 分页后的明细收尾 | 1.390 秒；先前已随分页预取，故此阶段不是全部明细请求历时 |
| 汇总及预览成本 | 约 23.1 + 8.8 ms |
| 两批持久回传 | 合计约 246.6 ms |
| 本机接收采用 / 利润读取计算 | 约 111.9 / 92.7 ms；与后续采集可重叠 |
| 采用状态定时检查 | 一次约 1.010 秒的等待；最终成本已采用后的剩余等待约 **0.913 秒** |
| 目录种子持久化 / 补全 | 约 21.2 / 5.8 ms，无新增 ERP 读取 |

代码中的界面收件定时器为 5000 ms，采集器等待采用时为 1000 ms。仅改变测试收件调度的正常 12 路对照如下，每组三次且采集计算、请求和结果保持一致；定时器相位固定在任务起点，真实任务的额外等待会随相位变化。

| 测试收件间隔 | 冷计算中位数 | 成本就绪中位数 [范围] | 任务墙钟中位数 [范围] |
| --- | --- | --- | --- |
| 25 ms | 2.897 秒 | 3.444 [3.431–3.460] 秒 | 4.459 [4.452–4.472] 秒 |
| 5000 ms | 2.914 秒 | 5.254 [5.243–5.297] 秒 | 5.503 [5.479–5.508] 秒 |

本样本中成本就绪额外等待约 1.810 秒，任务结束约多 1.044 秒；两级轮询存在重叠，不能机械相加成“固定浪费 6 秒”。本机核算约 0.2 秒，尚非这 10 个目标的主要瓶颈，故未扩展 CPU/内存专项；大型真实账本的表现仍待单独测量。

## 正确性、复现与交付

43 次均核对精确 SKU/SKC/仓库对应、越界映射排除、每目标全部 48 个采购记录 ID/数量/单价、选中的三条记录、CNY 成本 5、利润 88.6；每批五个目标全部采用，异常/缺证/缺失/待处理计数均为零。所有冷/热语义、最终成本及利润摘要一致。这里只含正常采购证据加传输故障，更多业务异常由以下既有回归覆盖。

- `pnpm --dir frontend test src/data/manualCostOverride.integration.test.js src/data/erpAutomaticAdoption.integration.test.js`：**2 文件 / 58 项通过**，覆盖人工优先、真实零值与微小正数、撤销恢复、范围归属、异常隔离与定稿/锁定保护。
- `node tools/erp-collection-time-budget.test.mjs`：虚拟长时钟的 80 秒请求、超过五分钟成本采集、超过一分钟目录补全及取消通过；与上述生产 120 秒实等验证分别记录。
- 测量入口：[原生基准](../../desktop/erp-speed-benchmark.mjs)、[隐藏主程序](../../desktop/erp-speed-benchmark-app.cjs)、[合成数据与断言](../../tools/fixtures/erp-speed-fixture.cjs)、[副本计时钩子](../../tools/fixtures/erp-speed-instrumentation.cjs)、[实际本机采用入口](../../tools/fixtures/erp-speed-local-entry.js)。
